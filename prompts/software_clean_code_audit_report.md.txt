### 🧱 Architectural & Craftsmanship Checklist

#### 1. Domain-Driven Design (DDD) & Boundary Integrity
*   **Ubiquitous Language:** Class, variable, and method names must map directly to business domain terms, avoiding technical jargon or database schema terms in core logic.
*   **Rich Domain Model vs. Anemic Domain Model:** Entities must encapsulate behavior, invariants, and business validation. Pure data bags (Getters/Setters only) with logic leaked into services should be flagged.
*   **Tactical DDD Patterns:** Proper identification and isolation of **Aggregates** (and Aggregate Roots), **Entities**, **Value Objects**, **Repositories**, and **Domain Services**. *Example: Ensuring a Value Object handles its own validation rules inherently upon instantiation.*

#### 2. Clean & Hexagonal Architecture (Ports & Adapters)
*   **The Dependency Rule:** Dependencies must only point inwards. The core Domain/Application layers must have zero awareness of databases, web frameworks, UI, or external APIs.
*   **Ports & Adapters Separation:**
    *   **Ports (Inbound/Outbound Interfaces):** Core application interfaces defining *what* the system needs to do.
    *   **Adapters (Driving/Driven Concretions):** Framework-specific code implementing those ports (e.g., REST Controllers, SQL Repositories, Kafka Consumers). *Example: Changing a database technology should only require writing a new adapter without touching core business logic.*

#### 3. SOLID Design Paradigms
*   **Single Responsibility (SRP):** Classes/modules must have exactly one reason to change.
*   **Open/Closed (OCP):** Software entities must be open for extension but closed for modification via interfaces or polymorphism.
*   **Liskov Substitution (LSP):** Derived classes must completely fulfill the behavioral contract of their base types.
*   **Interface Segregation (ISP):** Splitting heavy, bloated interfaces into slim, cohesive, role-based role interfaces.
*   **Dependency Inversion (DIP):** High-level business logic must depend on abstractions (interfaces/Ports), never on low-level details (Adapters/Concretions).

#### 4. Clean Code Principles
*   **DRY (Don't Repeat Yourself):** Elimination of duplicated logic or knowledge duplication.
*   **KISS (Keep It Simple, Stupid):** Avoidance of speculative complexity, deep nested conditionals, and over-engineered abstractions.
*   **YAGNI (You Aren't Gonna Need It):** Complete removal of dead code, unused dependencies, or speculative features built for "future requirements."
*   **Self-Documenting Abstractions:** Clear structural layout and intent-revealing code that eliminates the need for explanatory comments.
